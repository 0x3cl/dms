# DocTrack agent guide

Laravel 12 / PHP 8.2+ with Inertia 2, **Vue 3 inline-template `.js` pages**, Tailwind 4, Pest, and Pint. Follow the code immediately adjacent to the change; do not scan `CLAUDE.md` or unrelated modules for ordinary focused work.

## Load context by impact

1. Start with the requested file, its direct caller/route, the sibling implementation, and the closest test.
2. Expand one hop only when the change affects a contract: route/controller/page; model/migration/relationship; or a shared component and its consumers.
3. Read `CLAUDE.md` only for cross-module work, a new flow, or an unresolved design question. Search exact symbols with `rg`; do not bulk-read source trees.
4. For the design system — tokens, component APIs, page recipes — read `documentation/design-system.md` before writing any page or component.

## Working rules

- Use `php artisan make:* --no-interaction` for generated artifacts. Do not add dependencies or new top-level directories without approval.
- Run `vendor/bin/pint` after PHP edits, and `npm run build` (or `npm run dev`) after frontend edits — a Vue inline template only fails at build time.
- Add focused regression coverage for behaviour changes and run the narrowest relevant test: `php artisan test --compact --filter=testName`.
- Keep routes, controllers, models, Inertia props and page prop names aligned. Use named routes where the surrounding code does.

## Non-obvious invariants

- **Vue components are plain `.js` files, not `.vue` SFCs.** Every file in `resources/js/pages` and `resources/js/components` is `defineComponent({ template: \`...\` })`. `vite.config.js` aliases `vue` to the runtime **+ compiler** build specifically to compile those inline template strings; do not "fix" that alias or introduce an SFC without checking first, because page resolution in `app.js` globs `./pages/**/*.js`.
- **Card, panel, drawer and modal titles are `uppercase tracking-wide`.** The only exception is the page-title `<h1>` in `AdminShell`'s sticky header and the landing hero.
- **`border-rose-500` on an invalid input is load-bearing.** The global `router.on('error')` hook in `app.js` scrolls to and focuses the first element carrying it. Rename it and validation stops taking the user to the problem.
- **Dark mode is a variable remap under `html.dark`, never a `dark:` variant.** `resources/css/app.css` rewrites Tailwind's `--color-*` custom properties, so a utility keeps its intent and only its value changes. Do not add `dark:` classes — they would be the only ones in the codebase and would fight the remap. `--color-white` is deliberately *not* remapped (it is both a card surface and a button label), so `.bg-white` is patched per-utility instead.
- **A page's own `<main>` must carry `flex-1`.** `app.js` wraps every page in `flex min-h-screen flex-col` between the navbar and footer. Inertia pages render `<Head>` and `<main>` as sibling roots, so Vue cannot fall a class through onto a fragment, and a short page without it leaves a white gap above the footer. `AdminShell` already does this; standalone pages (`index.js`, `auth/*`) must do it themselves.
- **A document has no lifecycle.** The End Action is gone — route, controller method, `App\Enums\DocumentStatus`, `DocumentAction::Ended`, `StatusBadge` and the `documents.status` / `ended_at` columns. An uploader who wants a document out of circulation deletes it (soft, so the trail survives). Do not reinstate a status column "for later": a lifecycle state nothing writes is what produced the permanently-zero dashboard count.
- **"My Documents" and "All Documents" are one page with three tabs**, and the All tab's grant (`documents-all.read`) is resolved **in the controller**, not by middleware — a tab is a filter on one screen, so an unreachable one degrades to "Uploaded by me" rather than refusing the page. `/documents/all` is a redirect. The upload screen is `/documents/upload`, still named `documents.create`.
- **Shared with Me is a filter on My Files, not a screen.** At the top of a person's own storage, items shared *with them* are listed beside their own, queried from `item_shares` directly — not through `scopeVisible()`, which would also admit every public item and the administrator's reach. Each row's `access` badge comes from the **grant's `AccessSource`**, never from comparing `user_id`.
- **Sharing from the drawer is link-based only.** People are named where the thing is created (the New folder dialog, the document upload form). `ShareController::store()` and the directory the share-state endpoint used to ship are gone; revoking stays.
- **A delete carries a four-digit code the server issued.** `App\Services\Files\DeletionConfirmation` holds it in the session, spends it on use, and the endpoint refuses a mismatch. Never move that check into the browser — a code the page invents and verifies is a label on a button. `PURPOSE_DELETE` and `PURPOSE_PURGE` are separate on purpose.
- **A restore puts an item back under the chain above it**, reviving trashed ancestors (with `withTrashed()`, because the soft-delete scope hides exactly the folders that need reviving), reattaching to the owner's root when that chain cannot be rebuilt, and **renaming rather than refusing** on a collision — a restore has no second chance to ask.
- **Every name check uses `withTrashed()`.** `(folder_id, name)` and `(parent_id, name)` are unique over soft-deleted rows too, so a name held by something in the trash is still taken; leaving them out turned an ordinary re-upload into a 500.
- **A structural operation records its own failure.** `FileManager::attempt()` wraps the transaction behind move, copy, delete, restore and purge, writes an `outcome: 'failed'` row **after** the rollback — inside, it would be rolled back with the work it was recording — and re-throws untouched. Authorization refusals are deliberately outside it.
- **The page never chooses a preview viewer.** `App\Services\Files\FilePreview` resolves it behind the `view` ability, and for Word/Excel/PowerPoint mints a **signed, expiring** URL to `files.viewer` for **Microsoft's Office viewer** to fetch — the one door the private disk opens without a session. A PDF is never sent there (that viewer cannot render one); it streams from us and the browser renders it. Never for a confidential item, and the visibility is re-checked on every fetch, because an item can be reclassified after a URL is handed out.
- **An embedded viewer fetches from *our* server, not from the browser.** `FilePreview::viewerCanReachUs()` reads `app.url` and mints nothing when it is `localhost`, a `.test` domain or a private range — a frame pointing at an unreachable host stays empty forever, and an honest "download to view" beats a spinner. This is why document previews never work on a developer machine.
- **An account with no photo and no seed still has a face.** `resources/js/avatar.js` generates one from the person's name; `users.avatar_seed` is a deliberate pick. A photo and a seed are **exclusive** — setting either clears the other, and the uploaded bytes go with it.
- **Access is role-based, and the two halves are one mechanism.** Permissions are `{module}.{action}`; the whole vocabulary is `App\Support\Modules` and the two built-in roles are `App\Support\Roles`. `files.manage` gates Browse Storage as well as the administrator's read — `files-browse.read`, `files-shared.read` and `files.write` have been **retired**, because a permission that gates nothing is a checkbox granting nothing. A module's routes carry `permission:` middleware in `routes/web.php`, and `AdminShell`'s `MODULES` entries each name the permission that reaches them. **Add an entry and you add its route gate in the same change** — a hidden sidebar entry over an open route reads as protection that is not there. `SUPERADMIN` is short-circuited by the `Gate::before` hook in `AppServiceProvider`, so it is never enumerated. See `documentation/architecture.md` → Access model.
- **A module permission is not a per-record permission.** `documents.delete` says the capability exists for this user; `DocumentController::owns()` still decides which document it applies to. Withholding the module permission would not protect anyone else's upload — it would stop a user withdrawing their own.
- **Sign-in is by `employee_id`, not email.** `users.email` is nullable and exists only so Laravel's password broker has something to look an account up by; an account without one cannot self-serve a reset. Authentication goes through `LoginRequest`, which is where the rate limiting lives — never inline `Auth::attempt()` in the controller again.
- **There is no email verification.** `users` has no `email_verified_at` column and `User` does not implement `MustVerifyEmail`. Reinstating it means adding both first; `routes/auth.php` says so too.
- **Tutorials are frontend-only** — no route, no table, no permission of their own. A tour declares the `permission` of the feature it teaches and the menu filters on `auth.permissions`. A step's element is pointed at by a `data-tour` attribute, and **an anchor a tour references but no markup defines is a silent break**: the step is dropped or falls back and nothing fails. Scan the tour files for `[data-tour="…"]` and diff against the markup after adding a step.
- **Soft delete protects the *link*; hard delete protects the *history*.** `users`, `divisions`, `sections` and `documents` are soft-deleted, so a closed account cannot sign in while everything it owns still knows who owns it. Audit rows keep `nullOnDelete` beside a name snapshot, because the trail must survive a permanent erasure too. **In a test, `delete()` is the soft one** — if you mean "the row is gone for good", write `forceDelete()`.
- **An account that owns anything cannot be closed without an ownership transfer.** `OwnershipTransferService` moves folders, files and documents and deliberately does *not* touch the audit trail or `documents.uploader_name` — ownership is a fact about now, an audit row a fact about then. It never moves a root folder: two roots breaks the uniqueness the tree depends on, and MySQL would not catch it.
- **Upload limits are a row, not a literal.** Both upload paths go through `App\Services\Files\UploadPolicy`, which reads the administrator-editable `upload_settings` row for its scope (`documents` kept narrow, `files` broad). Extension **and** sniffed MIME type are both checked, and `prohibited_extensions` is applied last so it overrides the allow-list. The limits sent to the browser are a courtesy; the server is the gate.
- **An archive never chooses a path.** `ZipArchive::extractTo()` is never called — every entry is streamed out and written to a path built by `FilePathFactory` from a fresh `public_id`, which is what makes zip-slip impossible rather than filtered against. Validate the whole archive *before* opening the transaction, and collect every written path so a rollback can unlink them: disk writes are not transactional. See `documentation/modules/upload-settings.md` for the bomb, symlink, nesting and encryption guards.
- **Every file-manager operation goes through `App\Services\Files\FileManager`**, which resolves the ability on the subject *and the destination*, transacts, and writes the audit row. The controllers validate shape and hand over — none of them decides access. Checking only the subject lets a share on one folder deposit files into another the user cannot write.
- **A dual-view list keeps `view` in the query string** and renders one paginator through both bodies. That is what makes "switching views preserves page, filters, sort and search" true by construction rather than by a behaviour that drifts.
- **Row-level actions come from a server-resolved `can` object** on each payload, never from reading `auth.permissions` in a template — otherwise a read-only share shows a Delete button.
- **The one exception to `scopeVisible()` is "what was *given* to me".** The shared entry points at the top of My Files are queried from `item_shares` directly, because `scopeVisible()` also admits public items and the administrator's reach, which nobody gave anyone. Every other listing goes through the scope.
- **Every listing of files or folders must go through `AccessResolver::scopeVisible()`.** It is the same rule as `grant()` expressed in SQL. Fetching broadly and filtering in PHP afterwards is a leak: the paginator totals are wrong and those totals disclose existence even when the row is never rendered. `FileListingTest` holds a differential test that resolves every row through `grant()` and asserts the listing returns exactly that set — it has caught two real bugs already.
- **`files.storage_path`, never `files.path`.** `folders.path` is the materialized *ancestor* path; a file's ancestor path is its folder's path plus that folder's own id. When both columns were called `path` the SQL searched a file's **disk** path for a folder id, which never matches — so every ancestor rule silently evaluated as "no ancestors", listing a private folder's public file to everyone. `AccessResolver::ancestorPathSql()` is the one place that distinction lives.
- **Inheritance, in one sentence each:** effective visibility is the **most restrictive** value on an item and every folder above it, excluding the account's root (a container, never rendered, created private — leaving it in clamps everything to private); shares travel **downward** and the **nearest** ancestor carrying one wins; a share on the item itself beats anything inherited; **confidential** is reachable only by a share naming the item, never inherited and never via a link. See `documentation/modules/sharing.md`.
- **A share link never grants write, and a confidential item can never have one** — checked at creation *and* on every redemption, because an item can be reclassified after a link is handed out. On the share and file-stream routes **every** refusal is a 404, deliberately unlike the rest of the app: a 403 would confirm the token or identifier is real.
- **`App\Services\Access\AccessResolver` is the single place access to a file, folder or document is decided.** `DocumentController::isAuthorized()` / `::owns()` and `DocumentLogController::canSee()` all delegate to it. Those first two used to be hand-copied duplicates of each other, each carrying a comment saying the pair had to change together; one resolver is the only thing that stops that being something a future change must remember. The document clauses are reproduced in it verbatim and in order, because `tests/Feature/DocumentAuthorizationTest.php` is their contract.
- **Those callers keep returning a redirect, not a 403.** `DocumentAuthorizationTest` asserts `assertRedirect('/dashboard')` with a flash. Use `Gate`/resolver checks plus `unauthorizedRedirect()`; do not switch them to `$this->authorize()`.
- **Only the uploader may edit or delete a document** (`::owns()`). Both checks are load-bearing: without them any authenticated user could rewrite or delete any document in the office.
- **`documents` carries no state columns at all.** `status`, `ended_at`, `is_ended`, `target_division_id`, `target_section_id` and `document_logs.status` have all been dropped — the first two with the End Action, the rest as leftovers nothing read.
- **QR labels are SVG, not PNG.** `simple-qrcode` renders PNG through BaconQrCode's Imagick backend, and these servers have GD but not Imagick, so `format('png')` threw on every upload. Labels are named after the tracking code (`{code}.svg`) — never the document title, which is arbitrary user input that collided and, on a public download route taking the filename, was a traversal risk. `downloadQr()` matches the requested name against a stored `qr_code_path` before touching the disk, so older `.png` rows keep working.
- **A tracking code is per type, per day, sequential:** `ABBR-YYYYMMDD-NNNN`, issued only by `App\Services\TrackingCodeService::issue()`. The counter is `max(highest code on record, the document_series row's counter) + 1` under a row lock; both halves are load-bearing (import continuity, and never reissuing a deleted document's code). It is not "documents created today", which handed out duplicates as soon as two types were uploaded on one day.

- **Document types are a table, not a constant.** `document_types` is both the list the upload form offers and the map to code prefixes; `code` is immutable in practice because it is stamped into every code that type has issued. Retire a type with `is_active`. `DocumentTypeSeeder` is not sample data — nothing can be uploaded without it, which is why `Tests\TestCase` seeds it.

- **There are three audit tables and the difference is the audience.** `document_logs` is a document's travel history, shown to **everyone who can read that document**; `document_downloads` is the narrow "a copy left" register with its IP; `activity_logs` is everything that happens to a file or folder, behind `activity-trails.read`. Only `previewed` and `downloaded` cross from the third into the first — a `copied` or `extracted` row in a document's trail would disclose the file manager to every reader of the document. `App\Services\Files\FileEventRecorder` is the one place they are written together.
- **Write audit rows only through their single factory**: `DocumentLog::record()`, `DocumentDownload::register()`, `ActivityLog::record()`. A second construction site is how a table ends up with rows missing the actor's office.
- **Preview is debounced, download is not.** An iframe re-requests on every re-render, and a row per render is a forged history. Each download is a separate copy leaving the server. Both existence checks run *before* the record, so a missing file never leaves a record of a release that did not happen.
- **No audit row ever carries a live credential.** A share link's token is never recorded: it would make the audit report a way to obtain the credential.
- **Audit rows snapshot their actor; they do not join one.** `document_logs` and `document_downloads` carry `actor_name` / `user_name`, `division_name` and `section_name` beside the foreign keys, and the pages render the snapshots. Write them only through `DocumentLog::record()` and `DocumentDownload::register()`, which is the one place the shape is built. Every foreign key on an audit row is `nullOnDelete` so the row outlives what it points at — including `documents.user_id`, which used to cascade and delete a departing user's documents.

- **`document_logs.action` is an `App\Enums\DocumentAction`**, and only `DocumentAction::postable()` may be submitted by a user. The hand-off endpoint used to accept any string up to 255 characters.
- **File responses must stay out of Inertia.** `accessFile`, `receiveFile`, `downloadQr` and `files.stream` return file responses, which an Inertia XHR visit cannot follow. Reach them with a plain `<a href>`, a real form post, or `window.location` — never `router.visit`. `documents/show.js` posts the receive form directly for exactly this reason, which is also why it reads the CSRF token out of the meta tag.
- **Files live on the private `documents` disk and are served only by a controller.** Nothing is under `public/storage` any more: uploads used to go to the `public` disk, so every document was readable at `/storage/documents/<hash>.pdf` with no check at all. Read and write bytes through `App\Services\Files\FileStorage` and build paths only in `FilePathFactory` — never `storage_path()` interpolation, which is also what made these paths untestable under `Storage::fake()`.
- **A file URL is `/files/{ownerPublicId}/{filePublicId}`**, both 26-character opaque `public_id`s constrained in the route, so traversal is refused by the router. The owner segment is verified against the file's real owner, and every refusal is a 404 — a 403 would confirm the identifier exists. See `documentation/modules/files.md`.
- **`document_logs` and `document_downloads` are different things.** The first is the document's human-readable travel history, shown to anyone who can read the document. The second is the narrower "a copy left the server" register behind `/admin/download-logs`, and it carries the IP a copy went to, which has no business on a document page. A download writes both, and the second points at the first through `document_log_id`.

- **Divisions and sections carry a `code` as well as a `name`**, and a section's code and name are unique *within* its division — two divisions may each run a "Records" section, but one may not run two. **There is no separate employee directory any more** — `employees` was merged into `users` and dropped, so one person is one row and one sign-in. A person's name is stored as `first_name` + `last_name`, and `name` is a **derived** column the model's `saving` hook assembles from them: never write it directly, because the next save overwrites it. It stays a real column because audit snapshots and `files.owner_name` copy it and a query cannot call an accessor.
- **Flash keys are `success` and `error`, nothing else.** Both are shared by `HandleInertiaRequests` and watched by `AdminShell`, which opens a `FeedbackModal`. There is no toast component. Controllers that flashed `status` were normalised; do not reintroduce a third key.
- **Tests run against MySQL, not SQLite** (`dms_test`, see `phpunit.xml`): the deployment target ships `pdo_mysql` but not `pdo_sqlite`.
- `routes/auth.php` is registered by `bootstrap/app.php`'s `then:` callback. It went unloaded for the whole of the app's first life, which is why password reset never worked. Do not redeclare login/register/logout in `web.php` — they were duplicated in both files and whichever loaded last silently won.

## Keeping docs current (living-docs rule)

When a module's controller, model or page changes materially, or a module is added, update its context doc in the same change:

- Context doc: `documentation/modules/<module>.md`
- Design-system changes (a new shared component, a token, a page recipe): `documentation/design-system.md`
- Cross-module architecture and "why": `CLAUDE.md`

`documentation/project-stack.md` owns the stack and directory overview; `documentation/migration-notes.md` is a historical record of the Blade-to-Inertia conversion and should not be rewritten, only appended to.
